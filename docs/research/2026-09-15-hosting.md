# Free hosts for the label-check prototype, checked against the 5-second budget

Sources read 2026-09-15. All facts below are from primary vendor documentation (official `docs.*`,
pricing pages, or an official vendor blog post), each cited by URL at the point it's used. Anything
not confirmed in a primary source is marked "not found in primary docs" rather than filled in from
general knowledge. Anything from a vendor's own marketing copy rather than a documented spec is
marked "vendor-reported."

**Answer.** For shape (a) — the app just calls a hosted vision model — **Render** is the best free
fit: a real no-card Docker free tier, but its own docs state a ~1-minute cold start after 15 minutes
idle, so it needs an external keep-warm ping to meet the 5-second budget; **Google Cloud Run** is the
fallback if a Google Cloud billing account (card required, but usage should stay inside the Always
Free quota) is acceptable. For shape (b) — local CPU OCR needing 1.5-2GB RAM — no host's free tier
has enough RAM to run this without paying something: **Fly.io** (its documented cold-start figure,
~2+ seconds, is the fastest of any host checked) is the recommended cheap option once its 7-day/2-hour
trial ends and a card is added; **Oracle Cloud Free Tier**'s Always Free VM (2 OCPU/12GB, genuinely
$0 forever) is the true-zero-cost alternative, at the cost of doing your own Docker/TLS/reverse-proxy
setup and accepting Oracle's own documented signup-capacity risk. Hugging Face Spaces, assumed free
in the brief, turned out **not** to be: Docker Spaces now require a paid $9/month plan to even create.

## Shortlist: shape (a) — calls a hosted vision model, 256-512MB RAM

1. **Render** (recommended). Free Docker web service, no credit card
   ([render.com/docs/free](https://render.com/docs/free); no-card claim also stated in Render's own
   comparison article,
   [render.com/articles/platforms-with-a-real-free-tier-for-developers-in-2026](https://render.com/articles/platforms-with-a-real-free-tier-for-developers-in-2026)).
   Trade-off: Render's own docs say a free service "spins down" after 15 minutes with no inbound
   traffic and "spins back up... This process takes about one minute" on the next request
   ([render.com/docs/free](https://render.com/docs/free)) — a full minute is far outside the 5-second
   budget and close to the 30-40-second failure the brief describes. This is only survivable with an
   external keep-warm ping (see below); without one, a reviewer's first click during a cold window
   fails the requirement outright.
2. **Google Cloud Run** (fallback). Generous Always Free quota (2M requests/month, 180,000 vCPU-seconds,
   360,000 GiB-seconds — [docs.cloud.google.com/free/docs/free-cloud-features](https://docs.cloud.google.com/free/docs/free-cloud-features)),
   default request timeout of 5 minutes extendable to 60
   ([docs.cloud.google.com/run/docs/configuring/request-timeout](https://docs.cloud.google.com/run/docs/configuring/request-timeout)),
   and idle instances are kept warm for up to 15 minutes after the last request to reduce repeat cold
   starts ([docs.cloud.google.com/run/docs/about-instance-autoscaling](https://docs.cloud.google.com/run/docs/about-instance-autoscaling)).
   Trade-off: "A Google Cloud billing account is required to access the Google Cloud Free Tier"
   ([docs.cloud.google.com/free/docs/free-cloud-features](https://docs.cloud.google.com/free/docs/free-cloud-features))
   — a card must be on file even though qualifying usage isn't charged — and Google's docs give no
   specific cold-start time in seconds, so the actual first-hit latency for a small image is unverified.

## Shortlist: shape (b) — local CPU OCR, 1.5-2GB RAM, a few cores

No host's genuinely-free tier has enough RAM for this (Render free is 512MB, Railway free is
0.5GB, Koyeb free is 512MB, Azure F1 is 1GB — all short of the 1.5-2GB need). The realistic choices
both cost a small amount or a large amount of setup effort, fitting the owner's "free or cheap"
preference on the cheap side rather than the free side:

1. **Fly.io** (recommended, cheap not free). Fly's own docs give the fastest documented cold-start
   figure of any host checked: "Resume from suspend: a few hundred ms" vs. "Cold start: ~2+ seconds
   for common apps" ([fly.io/docs/reference/suspend-resume](https://fly.io/docs/reference/suspend-resume)),
   and machines can be sized up to 2 vCPU/4GB even during the free trial
   ([fly.io/docs/about/free-trial](https://fly.io/docs/about/free-trial)), comfortably covering the
   1.5-2GB need. Trade-off: there is no ongoing free tier — only a "2 hours of machine runtime or 7
   days of access, whichever comes first" trial, after which "all organizations... require a credit
   card on file" ([fly.io/docs/about/pricing](https://fly.io/docs/about/pricing)). Configuring
   `auto_stop_machines = "suspend"` keeps ongoing cost low for a low-traffic prototype.
2. **Oracle Cloud Free Tier — Always Free Ampere A1** (true zero cost, more setup). Currently 2 OCPU /
   12GB total, always free, no time limit
   ([docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)) —
   note this is roughly half the older commonly-cited 4 OCPU/24GB figure; the current number was
   confirmed directly against two current Oracle doc pages, not carried over from prior assumptions.
   Because it's a raw, always-on VM rather than a scale-to-zero platform, there is no cold start at all
   once it's running — the best fit for the 5-second budget by construction. Trade-offs: a credit card
   is required at signup even though it won't be charged unless upgraded
   ([docs.oracle.com/en-us/iaas/Content/FreeTier/freetier.htm](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier.htm)),
   and the box is unmanaged infrastructure — Docker, a reverse proxy, and TLS (e.g., Caddy or
   nginx + Let's Encrypt) all have to be set up by hand, which is a real time cost against the
   2026-09-16 21:00 deadline. Oracle's own docs also warn that "if you receive an 'out of host
   capacity' error... this indicates a temporary lack of Always Free shapes in your home region"
   ([docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)) —
   a documented availability risk, not just anecdote.

## Keeping the first request fast

- **Show an honest loading state.** If a host can cold-start, say so in the UI ("waking up the
  service, this can take a moment") rather than let a reviewer sit on a blank screen — this matches
  the brief's own emphasis on clarity for less technical staff.
- **External keep-warm ping.** For Render (15-minute sleep) or Koyeb (1-hour sleep), a free scheduled
  pinger (e.g., a GitHub Actions cron job, or a third-party free cron service) hitting a lightweight
  `/health` endpoint every 10-14 minutes prevents the sleep timer from firing during a reviewer's
  evaluation window. This is standing infrastructure, not a one-off trick, and it depends on the
  pinger itself staying up.
- **Lean on documented idle-retention windows instead of paying to stay warm.** Cloud Run and
  Container Apps both keep an idle instance ready for up to 15 minutes / do not bill while scaled to
  zero, so a light periodic ping (well within the free request quota) achieves the same effect without
  paying for `min-instances`.
- **Prefer suspend over stop on Fly.io.** `auto_stop_machines = "suspend"` resumes in "a few hundred
  ms" versus a full cold start's "~2+ seconds"
  ([fly.io/docs/reference/suspend-resume](https://fly.io/docs/reference/suspend-resume)) — still worth
  pairing with a keep-warm ping since the 5-second budget also has to cover the vision-model call or
  local OCR inference itself, not just the container boot.
- **Minimize what has to happen before the first response**, independent of host: keep the Docker
  image small, and lazy-load ONNX models rather than loading them at import time, since image size and
  process-boot time are within the developer's control regardless of which host is picked.

## Other findings worth the owner's attention

- **Hugging Face Spaces is not a free Docker host as of September 2026.** "Static Spaces are free for
  everyone. Gradio and Docker Spaces run on compute and require a paid plan to create: PRO for
  personal accounts, Team or Enterprise for organizations"
  ([huggingface.co/docs/hub/spaces-overview](https://huggingface.co/docs/hub/spaces-overview)), at
  $9/month ([huggingface.co/pricing](https://huggingface.co/pricing)). "CPU Basic has no hourly cost"
  describes the hardware's billing rate, not whether a Docker Space can be created at all. This
  reverses the brief's premise that it was a no-cost Docker candidate.
- **Koyeb's own docs explicitly restrict its free tier from this kind of use**: "Free Instances are
  restricted to a single region and cannot be used for production workloads or Worker Services"
  ([koyeb.com/docs/reference/instances](https://www.koyeb.com/docs/reference/instances)). A short
  evaluation prototype likely isn't "production" in the sense intended, but this is the most direct
  restriction language found among all vendors checked and is worth the owner's own read before relying
  on Koyeb.
- **Vercel's Hobby plan is restricted to "non-commercial personal use only"**
  ([vercel.com/docs/limits/fair-use-guidelines#commercial-usage](https://vercel.com/docs/limits/fair-use-guidelines#commercial-usage)).
  Whether a take-home built as part of a paid job application counts as "commercial" under Vercel's
  definition (use "for the purpose of financial gain of anyone involved in... the project") is
  genuinely ambiguous and not something to resolve unilaterally here. Separately, Vercel is
  architecturally a serverless-function platform, not a persistent-Dockerized-server platform, so it
  is a poor fit for the stated Docker-image approach regardless.
- **Azure App Service F1 has a genuine, unresolved primary-source conflict on Docker support.** The
  official current quickstart walks through selecting F1 for a Linux custom container in the Azure
  portal ([learn.microsoft.com/en-us/azure/app-service/quickstart-custom-container](https://learn.microsoft.com/en-us/azure/app-service/quickstart-custom-container)),
  while separate community sources (excluded here as non-primary, per this task's sourcing rule) claim
  Free/Shared Linux tiers don't support custom containers at all. No official page was found stating a
  blanket rule either way — this would need to be tested directly rather than assumed.
- **Azure fits the brief's own statement that the agency runs on Azure** (a 2019 migration, per the
  brief) — Container Apps' free grant (180,000 vCPU-seconds/month, 360,000 GiB-seconds/month, 2M
  requests/month — [learn.microsoft.com/en-us/azure/container-apps/billing](https://learn.microsoft.com/en-us/azure/container-apps/billing))
  is a real, documented, per-subscription allowance, not a time-boxed trial. But a card is required to
  create any Azure subscription
  ([azure.microsoft.com/en-us/pricing/purchase-options/azure-account](https://azure.microsoft.com/en-us/pricing/purchase-options/azure-account)),
  cold-start time isn't documented, and — by this doc's own arithmetic on the vendor's quoted numbers,
  not a vendor claim — a 24/7 minimum-size (0.25 vCPU) container would consume about 648,000
  vCPU-seconds/month, well over the 180,000 free grant, so it only stays free if it genuinely scales to
  zero between reviewer visits. Worth the platform-fit story, but not risk-free on the 5-second budget.
- **Cloudflare is not viable for either shape.** Workers cannot run a real FastAPI/Docker app (Python
  Workers run via Pyodide/WebAssembly, not a Linux container —
  [developers.cloudflare.com/workers/languages/python/how-python-workers-work](https://developers.cloudflare.com/workers/languages/python/how-python-workers-work)),
  and free-tier Workers get only 10ms of CPU time per request
  ([developers.cloudflare.com/workers/platform/limits](https://developers.cloudflare.com/workers/platform/limits)).
  Cloudflare Containers does run real Docker images but has no free tier at all — it requires the
  $5/month Workers Paid plan
  ([developers.cloudflare.com/containers/pricing](https://developers.cloudflare.com/containers/pricing)).

## Gaps — not verified from primary sources

- Cold-start duration in seconds: not documented by Google Cloud Run, Koyeb, Azure App Service F1, or
  Azure Container Apps. Only Render (~1 min) and Fly.io (~2+ s cold / ~hundreds of ms suspend-resume)
  give an actual vendor-stated number.
- Request/response body upload size limits: not found in primary docs for Hugging Face Spaces (app
  traffic), Render, Fly.io, Koyeb, Azure App Service F1, or Azure Container Apps. Confirmed only for
  Google Cloud Run (32 MiB per HTTP/1 request) and Railway (a 5-minute upload time window, not a byte
  cap). None of the checked vendors document a request-size limit framed around "a batch of 200-300
  images" — if that batch is uploaded as one request, it should be tested directly against whichever
  host is chosen, or better, uploaded as separate per-image requests to avoid an undocumented ceiling.
- Railway: whether its ongoing $1/month Free plan (distinct from the one-time $5 trial) requires a
  credit card is not stated in primary docs; only the paid Hobby tier's card requirement is confirmed.
- Koyeb: its FAQ page and its own official blog post disagree on whether a credit card is always
  required or only when automatic human-verification fails — reported as a genuine conflict, not
  resolved here.
- Whether Azure App Service F1 supports Linux custom containers at all is an open conflict between an
  official quickstart (implying yes) and general knowledge/community claims (implying no); no official
  page settles it either way.
- Oracle's documented exception letting Academy/CloudWorld/Sales-referred signups skip the credit-card
  requirement was seen only in a search summary, not confirmed against a primary Oracle doc page.
